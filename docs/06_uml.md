# UML
## Диаграмма вариантов использования (Use Case)
<img width="2340" height="4416" alt="image" src="https://github.com/user-attachments/assets/d1280fe4-05ae-4470-87be-a79375b97473" />
Диаграмма вариантов использования описывает функции системы DLP Tracker с точки зрения взаимодействия пользователей с веб-приложением. Выделены два актёра: Пользователь и Администратор, при этом Администратор является частным случаем Пользователя (наследует все его возможности) и дополнительно имеет права администрирования.

Пользователь может выполнить вход и выход из системы, просматривать список локаций, просматривать визиты по выбранной локации, добавлять, редактировать и удалять визиты, а также получать статистику по локации. Администратор, помимо перечисленных действий, выполняет управление пользователями: создание, изменение и удаление учётных записей. В диаграмме управление пользователями представлено как один вариант использования, который включает (include) операции создания, изменения и удаления пользователя.

## Диаграмма классов (Class)
<img width="3256" height="1484" alt="image" src="https://github.com/user-attachments/assets/296b5c64-b3d9-4b9c-b223-06f2358c3822" />

Диаграмма классов отражает структуру данных веб-приложения DLP Tracker и соответствует сущностям базы данных PostgreSQL. В модели выделены классы: Роль (Role), Пользователь (User), Локация (Location), Визит (Visit), Тег (Tag), а также промежуточный класс visit_tags (VisitTag) для реализации связи многие-ко-многим между визитами и тегами.

Пользователь хранит учётные данные и профиль (username, password_hash, full_name), а также связан с ролью через поле role_id, что позволяет разграничивать права доступа (обычный пользователь/администратор). Локация является справочником объектов, к которым привязываются визиты: одна локация может иметь множество визитов. Визит содержит основную информацию о посещении (дата, материал, сумма затрат, скидка) и хранит ссылку на пользователя, который создал запись (created_by), что обеспечивает учёт авторства изменений. Теги используются для дополнительной классификации визитов; поскольку один визит может иметь несколько тегов и один тег может относиться к разным визитам, связь реализована через таблицу-связку visit_tags, содержащую пары ключей visit_id и tag_id.

Таким образом, диаграмма показывает ключевые связи: Role–User (1 ко многим), Location–Visit (1 ко многим), User–Visit (авторство записи), а также Visit–Tag (многие ко многим через VisitTag).

## Диаграмма последовательностей (Sequence) — добавление визита
<img width="3456" height="3176" alt="image" src="https://github.com/user-attachments/assets/32346824-f418-4318-ba5b-312df931af2a" />

Диаграмма последовательностей описывает взаимодействие компонентов системы при добавлении нового визита. Инициатором сценария выступает Пользователь, который через браузер открывает форму создания визита. Веб-интерфейс отправляет запрос в Flask-приложение, после чего приложение обращается к базе данных PostgreSQL, чтобы получить необходимые справочные данные (например, список локаций для подстановки в форму), и возвращает пользователю HTML-страницу формы.

После заполнения полей формы пользователь отправляет данные, и браузер выполняет POST-запрос на сервер. Flask-приложение проверяет наличие активной сессии, затем выполняет валидацию введённых значений (дата, сумма, скидка и т.д.). Если данные корректны, приложение записывает новую строку в таблицу visits, фиксируя автора операции через поле created_by, и возвращает перенаправление на страницу списка визитов. Если проверка не пройдена, приложение возвращает форму с сообщением об ошибке, чтобы пользователь мог исправить введённые данные.
